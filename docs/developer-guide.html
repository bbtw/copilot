Retirement Plan Optimizer

A teaching guide for developers joining the system.

This guide explains how the LangGraph app passes state through the retirement planning pipeline, where domain decisions live, and how to make changes without blurring orchestration, optimization, simulation, and explanation responsibilities.

Orientation

The app is a compact simulation of a production retirement planning workflow. It starts with a fully populated customer profile, computes an optimized contribution plan, scores that plan with a Monte Carlo projection, fans out to three concurrent LLM analysis nodes, fans back in to synthesize a final explanation, and formats the result for display.

Treat the repository as two things at once: a runnable LangGraph example demonstrating fan-out / fan-in parallel execution with gateway-backed LLM calls, and a domain model for after-tax retirement contribution planning. The LP and Monte Carlo nodes are deliberately stand-ins; the LangGraph patterns they demonstrate are the point.

8

Graph nodes: two sequential data nodes, three concurrent LLM nodes, one synthesis node, and two bookend nodes.

11

State keys accumulated in RetirementPlanState as each node completes its work.

4

LLM calls per run: three analysis completions fire in parallel through the gateway, then one synthesis fan-in.

Mental Model

LangGraph is the orchestration layer. It decides which node runs next and carries state between nodes. The nodes are plain Python functions. A node reads the accumulated state, performs one responsibility, and returns a small dictionary containing the new values it produced.

The key idea: state is not a shared object that nodes mutate in place. State is an accumulated record assembled from each node's returned partial dictionary.

State Flow

src/lang_graph_state/main.py builds a StateGraph(RetirementPlanState) and invokes it with an empty dictionary. Two sequential data nodes run first, then three LLM analysis nodes fire concurrently, then a synthesis node fans them back in. The final state contains every intermediate value plus the assembled RetirementPlanResult.

Parallel Execution

LangGraph runs nodes concurrently whenever multiple outgoing edges share the same source node. No threading code is needed — the parallelism is declared entirely through graph wiring in src/lang_graph_state/main.py. 

# Fan-out: three edges from one node → three branches run simultaneously
graph.add_edge("run_monte_carlo", "run_standard_analysis")
graph.add_edge("run_monte_carlo", "run_accumulation_agent")
graph.add_edge("run_monte_carlo", "run_withdrawal_agent")

# Fan-in: LangGraph holds synthesize_explanation until all three have returned
graph.add_edge("run_standard_analysis",   "synthesize_explanation")
graph.add_edge("run_accumulation_agent", "synthesize_explanation")
graph.add_edge("run_withdrawal_agent",   "synthesize_explanation")

Each parallel node writes one PlanAnalysisSection to the shared analysis_sections key. LangGraph uses that key's explicit reducer to merge the three concurrent partial dicts before dispatching synthesize_explanation.

Gateway-backed analysis nodes

All three parallel LLM branches call ExplanationService. The accumulation and withdrawal branches run local deterministic probes first, then include those probe outputs in the prompt sent through the configured LLM gateway. 

def _build_analysis_node(*, service_call, build_probes, analysis_kind):
    async def run_analysis(state):
        request = _request_from_state(state)
        probe_results = build_probes(state)
        return {"analysis_sections": [PlanAnalysisSection(
            kind=analysis_kind,
            content=await service_call(request, probe_results),
        )]}
    return run_analysis

The graph nodes do not construct model clients. ExplanationService owns prompt assembly and delegates every LLM request to GatewayClient.

Node Contract

A key is any named value a node adds to the shared state object. When run_lp_optimizer returns {"contribution_allocation": ..., "projected_wealth": ...}, LangGraph merges that into state and those two keys are available to every node that runs after it. Each node reads the keys it needs and writes the keys it owns — nothing more.

The full set of valid keys is declared once in RetirementPlanState in src/lang_graph_state/domain/state.py. That is the team's agreement on what exists, what type it carries, and which node is responsible for it. Adding a key means adding it there first. 

# Plain function node — reads state, returns partial dict
def run_lp_optimizer(state: RetirementPlanState) -> dict[str, Any]:
    profile = state.customer_profile
    allocation, wealth, diagnostics = solve(profile)
    return {
        "contribution_allocation": allocation,
        "projected_wealth": wealth,
        "optimization_diagnostics": diagnostics,
    }

# Builder pattern — captures dependencies at build time, state at call time
def build_standard_analysis_node(svc: ExplanationService):
    async def run(state: RetirementPlanState) -> dict[str, Any]:
        return {"analysis_sections": [
            PlanAnalysisSection(kind="standard", content=await svc.astandard_analysis(state))
        ]}
    return run

# Gateway-backed analysis node — probes locally, then calls ExplanationService

A missing key at read time means an upstream node did not run or did not return what it should. That is always a graph wiring problem, not a value to default or skip.

Domain Model

The core domain types live in src/lang_graph_state/domain/models.py. CustomerProfile describes the customer's financial situation. ContributionAllocation holds the optimizer's annual recommendations before age 50 and after age 50. WealthDistribution captures Monte Carlo percentiles, ConfidenceBand classifies the projection result for internal explanation policy, and RetirementPlanResult packages the final user-facing output.

Keep domain terms aligned with CONTEXT.md. For example, SavingsCapacity means annual income minus annual expenses, and employer match dollars do not draw from that capacity. Using that term differently in code or documentation would create a real domain contradiction.

API Boundaries

In production, the LP optimizer and Monte Carlo engine are separate black-box API calls. This repository simulates both locally, but that is an implementation detail of v1. The only shared contract is the state keys each engine receives as input and the state keys it returns as output. Do not factor LP or Monte Carlo calculation rules into shared implementation code.

LP Optimizer API

Receives: customer_profile

Returns: contribution_allocation, projected_wealth

Deterministic. Maximizes projected after-tax wealth and produces the recommended annual contribution allocation across account types.

Monte Carlo API

Receives: customer_profile, contribution_allocation, projected_wealth

Returns: wealth_distribution, confidence_score, confidence_band

Stochastic. Scores the LP's recommended plan across simulated market and inflation paths and reports the spread of possible outcomes.

LLM Boundary

There are four LLM calls per run. All four are narration-only — they should not invent new allocations, modify confidence scores, or reinterpret the optimizer's objective.

Node Pattern Reads Returns
run_standard_analysis Single completion customer_profile, contribution_allocation, projected_wealth, wealth_distribution, confidence_score, confidence_band analysis_sections[kind=standard]
run_accumulation_agent LP probes + gateway completion customer_profile, contribution_allocation, projected_wealth, optimization_diagnostics analysis_sections[kind=accumulation]
run_withdrawal_agent MC probes + gateway completion customer_profile, contribution_allocation, wealth_distribution, confidence_score, confidence_band analysis_sections[kind=withdrawal]
synthesize_explanation Single completion (fan-in) analysis_sections, confidence_band explanation

Provider details belong behind src/lang_graph_state/services/llm.py. Graph wiring belongs in src/lang_graph_state/main.py. Prompt construction lives in the node files — src/lang_graph_state/nodes/standard_analysis.py, src/lang_graph_state/nodes/analysis_agents.py, and src/lang_graph_state/nodes/synthesize_explanation.py.

If you change a state key that feeds any LLM node, update the prompt in the corresponding node file. The LLM has no awareness of state — it only sees what the prompt explicitly passes.

Working Rules

When adding a sequential node

Add the state key to RetirementPlanState, define which upstream keys it reads, return only the keys it owns, and wire it with two add_edge calls in src/lang_graph_state/main.py. Update the state flow table above.

When adding a parallel node

Add an add_edge from the fan-out source (run_monte_carlo) to the new node, and an add_edge from the new node to the fan-in target (synthesize_explanation). Add its output key to RetirementPlanState and update the synthesize prompt.

When changing domain language

Update CONTEXT.md as soon as the term is resolved. The glossary is the source of truth for project-specific vocabulary.

When changing an LLM node

Update the prompt in the node's builder function. The LLM sees only what the prompt passes — changing a state key without updating the prompt silently degrades output quality. Check that generated language does not overstate certainty.
