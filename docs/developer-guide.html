Retirement Plan Optimizer

A teaching guide for developers joining the system.

This guide explains how the LangGraph app passes state through the retirement planning pipeline, where domain decisions live, and how to make changes without blurring orchestration, optimization, simulation, and explanation responsibilities.

Orientation

The app is a compact simulation of a production retirement planning workflow. It starts with a fully populated customer profile, computes an optimized contribution plan, scores that plan with a Monte Carlo projection, asks an LLM to explain the outcome, and formats the result for display.

Treat the repository as two things at once: a runnable LangGraph example and a domain model for after-tax retirement contribution planning. The code is intentionally small, but the boundaries matter because future versions are expected to replace local implementations with production APIs.

Mental Model

LangGraph is the orchestration layer. It decides which node runs next and carries state between nodes. The nodes are plain Python functions. A node reads the accumulated state, performs one responsibility, and returns a small dictionary containing the new values it produced.

The key idea: state is not a shared object that nodes mutate in place. State is an accumulated record assembled from each node's returned partial dictionary.

State Flow

main.py builds a StateGraph(RetirementPlanState) and invokes it with an empty dictionary. From there, each node adds the next piece of the plan. The final state contains both intermediate values and the assembled RetirementPlanResult.

Node Contract

A key is any named value a node adds to the shared state object. When run_lp_optimizer returns {"contribution_allocation": ..., "projected_wealth": ...}, LangGraph merges that into state and those two keys are available to every node that runs after it. Each node reads the keys it needs and writes the keys it owns — nothing more.

The full set of valid keys is declared once in RetirementPlanState in state.py. That is the team's agreement on what exists, what type it carries, and which node is responsible for it. Adding a key means adding it there first. 

def run_lp_optimizer(state: RetirementPlanState) -> dict:
    profile = state["customer_profile"]
    allocation, wealth = solve(profile)
    return {"contribution_allocation": allocation, "projected_wealth": wealth}

def run_monte_carlo(state: RetirementPlanState) -> dict:
    paths = simulate(state["customer_profile"], state["contribution_allocation"])
    return {
        "wealth_distribution": paths.distribution,
        "confidence_score": paths.confidence,
        "confidence_band": paths.confidence_band,
    }

def route_by_confidence_band(state: RetirementPlanState) -> str:
    return state["confidence_band"]

A missing key at read time means an upstream node did not run or did not return what it should. That is always a graph wiring problem, not a value to default or skip.

Domain Model

The core domain types live in models.py. CustomerProfile describes the customer's financial situation. ContributionAllocation holds the optimizer's annual recommendations before age 50 and after age 50. WealthDistribution captures Monte Carlo percentiles, ConfidenceBand classifies the projection result for internal explanation policy, and RetirementPlanResult packages the final user-facing output.

Keep domain terms aligned with CONTEXT.md. For example, SavingsCapacity means annual income minus annual expenses, and employer match dollars do not draw from that capacity. Using that term differently in code or documentation would create a real domain contradiction.

API Boundaries

In production, the LP optimizer and Monte Carlo engine are separate black-box API calls. This repository simulates both locally, but that is an implementation detail of v1. The only shared contract is the state keys each engine receives as input and the state keys it returns as output. Do not factor LP or Monte Carlo calculation rules into shared implementation code.

LP Optimizer API

Receives: customer_profile

Returns: contribution_allocation, projected_wealth

Deterministic. Maximizes projected after-tax wealth and produces the recommended annual contribution allocation across account types.

Monte Carlo API

Receives: customer_profile, contribution_allocation, projected_wealth

Returns: wealth_distribution, confidence_score, confidence_band

Stochastic. Scores the LP's recommended plan across simulated market and inflation paths and reports the spread of possible outcomes.

LLM Boundary

The graph routes to a confidence-specific explanation node after both API calls complete. Its job is narration only — it should not invent new allocations, modify confidence, or reinterpret the optimizer's objective.

Direction State keys
Input (reads) customer_profile, contribution_allocation, projected_wealth, wealth_distribution, confidence_score, confidence_band
Output (returns) explanation

Provider details belong behind llm_gateway.py. Graph wiring belongs in main.py. The route-specific explanation functions in nodes/explanation.py own prompt construction — they format the six input keys into a prompt, add confidence-specific guidance, and call the gateway.

If you change a state key that feeds the explanation node, update the prompt in nodes/explanation.py. The LLM has no awareness of state — it only sees what the prompt explicitly passes.

Working Rules

When adding a node

Add the state key to RetirementPlanState, define which upstream keys it reads, return only the keys it owns, and update this guide's state flow table.

When changing domain language

Update CONTEXT.md as soon as the term is resolved. The glossary is the source of truth for project-specific vocabulary.

When changing calculations

Add or adjust tests around the affected engine. LP tests should verify constraints and optimal allocation properties; Monte Carlo tests should verify shape and scenario behavior.

When changing explanations

Check that the prompt uses only facts available in state and that the generated language does not overstate certainty or present stochastic output as a guarantee.
