Codebase Guide

Retirement Planning Optimizer

A chat-driven retirement planner: you describe your situation in plain language, an LLM fills a typed Profile, and a Gurobi linear program finds the tax-optimal contribution, withdrawal, and Roth-conversion schedule. The LLM never computes a number itself — every figure in the reply comes from the solver.

Principle

LLM translates, solver decides

The chat interface is an LLM; the retirement math is a fixed, hand-written Gurobi LP formulation. The LLM's only job is translation in both directions — natural language into a typed Profile, solver output into narration — connected by one tool call, solve_plan. Click a step for what actually happens there.

01You describe your situation

Plain-language chat: ages, income, account balances, guaranteed income, and which objective to maximize. No form, no fields — the assistant asks for whatever it's still missing.

→
02LLM fills the Profile

The model's job here is translation only: natural language → the typed solve_plan arguments. It states the defaults it applied (5% return, 15% capital gains, $24,500 limit) so you can override them, and never invents a figure you didn't state.

→
03Gurobi solves the lifetime LP

model.py builds one linear program per call: a Contribution Split for the Accumulation years, a Withdrawal Schedule and Roth Conversions for Decumulation — subject to contribution limits, RMDs, and the age-60 early-withdrawal lock. Progressive tax brackets stay convex, so no binary variables are needed.

→
04LLM narrates the Plan

The full year-by-year table and a balance chart render in the app's Plan panel; the LLM only receives a compact summary and narrates that. Every number in its reply must trace back to the summary — rounded for readability, never computed or derived.

What-if questions ("what if I retire at 62?") are handled as Profile mutation + re-solve — never as the LLM extrapolating from a previous answer. Same loop, new inputs.

Language

Three accounts, two phases, one objective

Real-world account types (401(k), IRA) are collapsed into exactly three tax-treatment buckets. The system never distinguishes further than this.

Traditional

Pre-tax. Withdrawals are taxed as ordinary income. Shares one combined annual contribution limit with Roth ($24,500 default). Required Minimum Distributions start at 73, sized by the IRS Uniform Lifetime Table — why unconverted balances eventually get force-taxed.

Roth

Post-tax. Withdrawals are tax-free. Shares the same combined limit with Traditional. No RMDs, ever. A Traditional→Roth conversion is taxed as ordinary income in the conversion year and doesn't count toward RMD satisfaction.

Taxable

An ordinary brokerage account — unlimited contributions. Growth is taxed annually as a flat capital-gains drag (15% default) instead of tracking cost basis: a deliberate simplification that slightly over-favors the tax-advantaged accounts.

Accumulation · current age → retirement age The solver decides the Contribution Split: how Savings Capacity divides across the three accounts each year, under the contribution limit.
Decumulation · retirement age → plan horizon The solver decides the Withdrawal Schedule and Roth Conversions. Traditional/Roth withdrawals are locked before age 60 — if Taxable can't bridge that gap, the plan is infeasible. RMDs become a hard floor from age 73.

Every run maximizes exactly one Objective, measured in After-Tax Value — Roth and Taxable at face, Traditional at face minus what a bracket-taxed liquidation would cost. Raw balances are never compared across accounts.

Wealth at Retirement

After-Tax Value of the balances the instant Decumulation starts. Later years must still meet Spending Need, but don't affect the objective.

Terminal Wealth

After-Tax Value at the Plan Horizon — the end of Decumulation. What's left after a full retirement of spending.

Real dollars, always. Bracket thresholds, contribution limits, Savings Capacity, and Spending Need stay constant across plan years; Expected Return is a real (after-inflation) rate. No inflation parameter exists anywhere in the model.

Layout

Codebase map

Click a file for what it owns.

copilot/
agent.pyThe Agent — prompt, solve_plan tool, and the turn loop
Defines SYSTEM_PROMPT, the solve_plan tool schema, and run_turn() — the loop that calls the model, executes any tool calls, and repeats until the assistant replies in plain text. Each turn returns a TurnResult recording every solve (raw arguments, result dict, and the solved Plan), so the web UI and the eval harness read what happened instead of re-parsing the transcript.
web.pyLocal web UI — one frontend to the Agent
copilot's main(): a FastAPI server on 127.0.0.1 serving static/index.html plus JSON endpoints around run_turn(). The page is a chat transcript beside a Plan panel that keeps every solve of the session as tabs — year-by-year table and balance chart each.
model.pyThe Gurobi LP — builds and solves fresh on every call
solve(profile, objective) constructs one linear program per invocation: per-year contribution, withdrawal, conversion, and balance variables, with progressive-bracket income modeled as convex piecewise-linear segments (no binary variables). Checked against GUROBI_TRIAL_LIMIT = 2000 before optimizing — the free pip-license variable/constraint cap.
plan.pyThe Plan — the solver's output, and the only source of numbers
Plan / YearRow / Infeasible dataclasses, plus to_summary() (the compact dict handed to the LLM — the only thing it's allowed to narrate). The full year-by-year table is rendered client-side by the web UI.
profile.pyThe Profile — typed inputs the solver needs
The Profile dataclass (ages, balances, income, filing status, overrides), from_solve_args() — raw solve_plan arguments to one Profile + one Objective — and validate(), which raises chat-presentable ValueErrors for out-of-range ages, negative amounts, or a horizon before retirement.
taxdata.py2026 federal tax data and every model default
Progressive brackets and standard deduction by filing status, the IRS Uniform Lifetime Table for RMDs, and the defaults the chat mentions: 5% real return, 15% capital gains, $24,500 combined contribution limit, 85% Social Security taxable fraction, age-60 early-withdrawal stand-in.
copilot/evals/
run.pyEntry point — syncs Fact Cards, runs the LangSmith experiment
copilot-evals's main(). Mirrors repo Fact Cards up to a LangSmith dataset (repo is master), then calls evaluate() with the three evaluators and num_repetitions runs per Scenario, tagged with the git SHA and a hash of the system prompt.
scenario.pyDrives one Scenario: Simulated User vs. the real chat loop
run_scenario() alternates a Simulated User (an LLM reading only the Fact Card) with the agent's own run_turn(), up to TURN_CAP = 12, and captures the first solve_plan call.
scoring.pyThe two deterministic scorers, plus the sim-side audit
profile_fidelity(), number_faithfulness(), and audit_sim() — all plain dict/string comparisons, no LLM involved.
numbers.pyNumber extraction and significant-digit matching
Regex-based extract_numbers() plus matches_source(): a displayed figure matches if it equals a source value rounded to the digits actually shown.
cards.pyLoads and validates the Fact Card JSON files
load_cards() checks every card's expected_args against the live solve_plan schema, so a card can't drift from the tool it's testing.
cards/*.jsonSix Fact Cards — script and answer key in one file
See the explorer in Evals below for all six, grouped by family: happy_path, stated_overrides, infeasible_profile.

Try it

Running it

Requires Python 3.12+ and uv. Install once with uv sync, then set the env vars below in your shell, or drop them in a gitignored .env file in the repo root — copilot/settings.py (Pydantic Settings) loads it automatically, no shell sourcing needed.

# paste as-is into a gitignored .env, or run each line in your shell
export LLM_BASE_URL=...   # company gateway, or a local Ollama OpenAI-compatible endpoint
export LLM_API_KEY=...
export LLM_MODEL=...              # model name your gateway routes
export LANGSMITH_TRACING=true     # optional: full tracing
export LANGSMITH_API_KEY=...

uv run copilot

Starts a local server on 127.0.0.1:8765 and opens your browser. Gurobi runs on the free pip license (no license file needed); the model is sized to stay under its 2,000-variable / 2,000-constraint limit.

uv run pytest

The LP model (test_model.py), the Agent turn loop (test_agent.py), the web endpoints (test_web.py), plus one file per evals module — test_evals_cards.py, test_evals_numbers.py, test_evals_scenario.py, test_evals_scoring.py.

# paste as-is into a gitignored .env, or run each line in your shell
export LLM_BASE_URL=...   # company gateway, or a local Ollama OpenAI-compatible endpoint
export LLM_API_KEY=...
export LLM_MODEL=...              # model name your gateway routes
export LANGSMITH_API_KEY=...
export EVAL_SIM_MODEL=...   # optional: simulated-user model, defaults to LLM_MODEL

uv run copilot-evals --runs 3

Needs the same gateway vars as the web UI, plus LANGSMITH_API_KEY. --runs sets repetitions per Scenario (default 3). Fact Cards sync from copilot/evals/cards/ up to a LangSmith dataset on every invocation — the repo is always the master copy.

ADR-0004

Agentic evals: LLMs converse, code scores

The suite runs full conversations — a Simulated User improvising from a Fact Card against the real chat loop — but no LLM grades anything. Two dimensions only, both scored by deterministic Python.

01Fact Card

A JSON file in copilot/evals/cards/ — the ground truth. Its facts prose is the only thing the Simulated User may say; its expected_args is the exact solve_plan call the agent must produce.

→
02Simulated User ↔ chat loop

An LLM plays the user, improvising from the card. It talks to the same run_turn() the web UI uses — no eval-only code path on the agent side.

→
03Capture

The harness records the first solve_plan call's arguments and result, plus every message sent, up to a 12-turn cap. Reaching the cap with no solve is a "no-solve" — charged to the agent, not the harness.

→
04Score

Two scorers grade the run: Profile Fidelity and Number Faithfulness. Results land as a LangSmith experiment, tagged to the git SHA and system-prompt hash.

Profile Fidelity

Do the raw solve_plan arguments match the Fact Card exactly? Stated fields must match verbatim; unstated optional fields must be strictly absent — an agent that passes a default explicitly (e.g. expected_return=0.05 when the card never mentioned a return) fails, since it may have memorized the value rather than sourced it.

Number Faithfulness

Does every number in the agent's prose trace to an allowed source — the solve result, the Fact Card, an age within the plan, or a taxdata default — exactly or rounded to the digits shown? "$1.2M" matches 1,203,456; "$1.25M" doesn't. Derived arithmetic (e.g. "$40k/year" computed from a $320k total) always fails.

Voided Run. If the Simulated User states a number that isn't on its own Fact Card, the run is discarded and retried (up to 2 extra attempts) — charged to the sim side, never counted as an agent failure.

Design decisions

Four ADRs; each one constrains what the others are allowed to assume.

0001Convex tax model, pure LP

US bracket schedules are convex piecewise-linear (marginal rates only increase), and tax always hurts the objective — so brackets can be modeled with segment variables and no binaries. The tax model commits to staying convex: filing status + standard deduction + progressive federal brackets, flat capital-gains rate on Taxable, no state tax.

  • Anything that breaks convexity — Social Security benefit taxation phase-in, capital-gains bracket stacking, IRMAA cliffs, AMT — is out of scope until this is consciously revisited.
  • Adding one of those later means migrating LP → MILP, a formulation change, not just a feature.
  • Everything is in real (today's) dollars; no inflation parameter exists.
0002LLM translates, solver decides

Every financial number originates in solver output; the LLM never computes, estimates, or extrapolates a figure. Amended 2026-07-09: the LLM may now round a solver figure to displayed significant digits for readable narration — computing, estimating, and extrapolating remain forbidden.

  • The formulation is testable in isolation (golden profiles → expected plans), independent of any LLM behavior.
  • New capabilities require changing the formulation code — chat can't "unlock" behavior the LP doesn't have.
  • What-ifs are Profile mutation + re-solve, never LLM extrapolation.
0003LLM via an OpenAI-compatible client

All LLM calls use the standard openai package pointed at a configurable base_url — never a provider SDK, since none is available in production. The same client code targets either the company gateway or a local Ollama instance; wrap_openai plus @traceable on the solver give one LangSmith trace tree per conversation.

  • Model choice is configuration, not code — whatever the target routes.
  • No Anthropic-specific features (extended thinking, prompt caching controls) can be relied on.
  • If tool-calling passthrough ever breaks, the documented fallback is structured-output prompting — the ADR-0002 boundary survives, only the wire format changes.
0004Agentic evals: LLMs converse, code scores

Full conversations, deterministic scoring: LLM-as-judge was considered and rejected for v1 — both Profile Fidelity and Number Faithfulness are mechanically checkable, and a judge would reintroduce the nondeterminism the suite exists to control for.

  • Every Fact Card must uniquely determine correct agent behavior; cards needing interpretation (adversarial phrasing, mid-conversation corrections) are held out of v1 on purpose.
  • A fidelity or faithfulness failure is an agent failure by construction — sim-side faults are voided, no-solves are charged to the agent. No transcript needs a human read before a score is believed.
